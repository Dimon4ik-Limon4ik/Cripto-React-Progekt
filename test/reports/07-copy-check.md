# 07. Копия рабочей БД и проверки на копии (шаги 1–2)

- **Дата:** 15.11.2026
- **Окружение:** Windows 10.0.19045, Node.js **v24.11.0**, PostgreSQL/pg_dump **18.6**
- **Исходная база:** `my_crypto` — использована **только** для `pg_dump` (чтение).
- **Копия:** `my_crypto_copy_test` (в имени есть `test`), пересоздана с нуля.
- **Сервер:** запускался с `NODE_ENV=test` и `DATABASE_URL_TEST`, порт 3107, затем остановлен.

## Как обеспечена безопасность

| Требование | Как выполнено |
| --- | --- |
| Рабочая БД только на чтение | `pg_dump`, ни одного `INSERT/UPDATE/DELETE/DDL` в `my_crypto`; сервер против неё не запускался |
| Дамп не в проекте и не в git | файл создан в `%TEMP%\crypto-stage7-*\my_crypto.dump`, после восстановления удалён (проверено: папки нет) |
| Секреты не выводятся | логин/пароль читаются из `secrets/.env` через `dotenv` в рантайме, пароль передаётся только через `PGPASSWORD`; в лог/отчёт попадают лишь размеры и количества |
| `DATABASE_URL_TEST`/`NODE_ENV` только в среде процесса | задаются в `env` дочернего процесса, без `setx` и без записи в файлы |
| Никаких правок вне `test/` | изменялся только `test/` (скрипт и отчёты) |

Скрипт: `test/scripts/07-copy-check.mjs` (запуск: `cd test && npm run test:copy`).

## Шаг 2. Проверки на копии

### Запуск бэкенда в тестовом режиме

- `NODE_ENV=test`, `DATABASE_URL_TEST` → копия, `PORT=3107`.
- Сервер поднялся (`httpReady=true`) и был корректно остановлен (`stopped=true`).
- Строк `[schema]` в логе: **0** — `ensureUsersSchema` и `ensureFavoritesSchema`
  не нашли ни одной проблемы и ничего не меняли.
- Единственная служебная строка лога: `Сервер запущен на http://localhost:3107`.

### Read-only проверки копии

| Показатель | До запуска сервера | После запуска сервера |
| --- | --- | --- |
| Строк в `users` | 4 | 4 |
| Строк в `cryptoinfavorites` | 7 | 7 |
| `cryptoinfavorites.idusers IS NULL` | 0 | 0 |
| `cryptoinfavorites.idcrypto IS NULL` | 0 | 0 |
| Дубликаты пар `(idusers, idcrypto)` (лишние строки) | 0 | 0 |
| Избранное с несуществующим пользователем (сироты) | 0 | 0 |
| `NOT NULL` у `idusers` / `idcrypto` / `created_at` | да / да / да | да / да / да |
| PRIMARY KEY | `cryptoinfavorites_pkey(idcrypto, idusers)` | без изменений |
| FOREIGN KEY на `users(idusers)` с `ON DELETE CASCADE` | `cryptoinfavorites_idusers_fkey` — **есть, CASCADE** | без изменений |

**Вывод:** копия рабочей базы консистентна. Ограничения целостности на месте:
первичный ключ по паре `(idusers, idcrypto)` и внешний ключ на `users(idusers)`
с каскадным удалением. Строк, блокирующих создание ограничений (NULL, дубликаты,
сироты), нет — поэтому предупреждений `[schema]` не было, а `ensure*` ничего не
изменяли (состояние до и после старта идентично).

## Ограничения и решения в спорных местах

1. Копия создаётся в **той же** СУБД под учётной записью из `secrets/.env`; при
   отсутствии права `CREATEDB` скрипт упадёт с сообщением без секретов.
2. Дамп снят без `--clean` и без `--create` — рабочая база не затрагивается,
   восстановление идёт в заранее созданную копию.
3. Содержимое `pg_restore` stderr не выводится: оно может содержать фрагменты SQL
   с данными. В отчёт попадает только количество строк stderr.
4. Копия после проверок **оставлена** специально: на ней выполняются
   интеграционные тесты API (`test/api/`). Рабочая `my_crypto` не изменялась.
