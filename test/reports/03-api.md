### Про 403

В приложении нет ролей и маршрутов «по id другого пользователя»: все операции берут владельца из `req.user.userId` (JWT). Поэтому 403 не выдаётся ни при каких условиях — это зафиксировано тестом «попытки доступа к чужому аккаунту не дают 403 и не меняют чужие данные»: чужой `idusers`/`userId` в query и в теле игнорируется, данные жертвы остаются целыми, её пароль продолжает работать. Если в будущем появится админ-панель, эти тесты станут основой для проверки 403.

## Фактическая схема копии БД

Снята скриптом `test/scripts/03-schema-info.mjs` → `test/tmp/03-schema.json` (только метаданные, без данных).

| Таблица.колонка | Тип в копии | Ограничение |
| --- | --- | --- |
| `users.idusers` | `integer` | PK, NOT NULL |
| `users.name` | `varchar(100)` | допускает NULL |
| `users.login` | `varchar(100)` | UNIQUE, допускает NULL |
| `users.password` | `varchar(60)` | допускает NULL (ровно под bcrypt-хеш) |
| `users.email` | `varchar(100)` | UNIQUE, допускает NULL |
| `users.created_at` | `timestamptz` | NOT NULL |
| `cryptoinfavorites.idusers` | `integer` | PK (часть), FK → `users` ON DELETE CASCADE |
| `cryptoinfavorites.idcrypto` | `varchar(100)` | PK (часть) |
| `cryptoinfavorites.created_at` | `timestamptz` | NOT NULL |

**Расхождение, важное для дефектов:** `README.md` и `backend/services/ensureUsersSchema.js:8-16` описывают `name VARCHAR(50)`, `login VARCHAR(15)`, `password VARCHAR(255)`, `email VARCHAR(255) NOT NULL`, а в рабочей базе (и в копии) — `100/100/60/100` и колонки допускают NULL. `ensureUsersSchema` использует `CREATE TABLE IF NOT EXISTS`, поэтому существующую таблицу не приводит к «документированному» виду. Отсюда дефект №3: валидатор пропускает email длиннее 100 символов, а БД отвечает ошибкой `22001`, которую контроллер отдаёт как `500`.

| № | Критичность | Проблема | Тест |
| --- | --- | --- | --- |
| 1 | высокая | Нет ограничения частоты попыток входа и регистрации (брутфорс, перебор логинов/email) | `07` → «после серии неверных паролей должен появиться 429» |

## Принятые решения (там, где был выбор)

Выбраны самые безопасные варианты — вопросов не задавал:

1. **Vitest, а не Jest** — весь проект на ESM (`"type": "module"`), Vitest запускает ESM без транспиляции и дополнительной конфигурации. Уже установлен в `test/`, новые пакеты не добавлялись.
2. **Сервер отдельным процессом**, а не импорт `app` — `backend/server.js` не экспортирует приложение и сам вызывает `listen()`. Так тестируется реальная цепочка middleware, включая обработчик ошибок и `ensure*` при старте. Прод-код не менялся.
3. **Копия БД не пересоздавалась.** `scripts/03-ensure-copy.mjs` сначала проверяет наличие `my_crypto_copy_test` и создаёт её из `pg_dump` **только если её нет**. Пересоздание существующей копии означало бы потерю состояния, на котором прогонялись предыдущие этапы, поэтому от него отказался (безопасный вариант).
4. **Заглушка CoinGecko через `--import`** — реальные запросы к внешнему API сделали бы тесты недетерминированными. Заглушка подменяет только домен `api.coingecko.com`; добавлен кейс `stub-500` (5xx внешнего API). Реальные ключи в тестах не используются.
5. **Свои данные + точечная очистка** — тестовые аккаунты имеют email `@vitest.local` и удаляются по `idusers` после каждого теста; teardown сравнивает количества строк и падает при расхождении.
6. **13 красных тестов оставлены красными** — они фиксируют дефекты и должны позеленеть после исправлений; «зелёный» прогон через `it.fails`/`skip` скрыл бы проблемы.
7. **Граница email — 100 символов**, потому что так в фактической схеме `users.email`. Вариант «поднять лимит до 255 по README» потребовал бы `ALTER TABLE` на реальной БД (запрещено правилами), а вариант «не проверять» оставляет `500` на пользовательский ввод.
8. **Rate limiting не эмулировался** — дефект проверяется на реальном коде без лимитера (20 попыток входа). Порог и окно в тесте не фиксируются жёстко: проверяется только появление `429` в серии.
9. **403 проверяется эквивалентом** (см. раздел «Про 403»): ролей нет, поэтому вместо 403 тесты доказывают, что подмена id не даёт доступа.
10. **Вывод терминала** в этой среде плохо захватывается shell-интеграцией VS Code, поэтому логи команд пишутся в `test/tmp/*.log` и читаются оттуда. Это не влияет на код тестов; все артефакты внутри `test/`.

## Ограничения этапа

- Только API: браузерных E2E-тестов, нагрузочных и fuzz-тестов в этом этапе нет.
- Внешние сервисы проверяются по заглушке — реальные ответы CoinGecko (формат, лимиты) не верифицируются.
- Проверка изоляции сравнивает **количества** строк, а не контрольные суммы содержимого: изменение значений существующих строк тем же количеством тестом не обнаружится (тесты этого и не делают — все проверки идут по своим `@vitest.local`-аккаунтам).
- Один процесс бэкенда и последовательное выполнение файлов (`fileParallelism: false`) — так проверка изоляции детерминирована; цена — ~19–21 с на прогон.
- Границы длин полей привязаны к схеме копии (100/100/60/100); после исправления схемы/валидаторов тесты `08` нужно перепроверить.
